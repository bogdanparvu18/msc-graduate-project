## Executive summary

This notebook constructs temporal evidence around the representative verified frame of each eligible S5 finding segment. It consumes the current, checked S1–S5 chain from a pinned GitHub `main` commit, copies the required source files from Google Drive to local Colab SSD storage, and verifies the local bytes against the committed upstream SHA-256 references. It then builds bounded temporal windows, reuses official labelled images where available, extracts missing context images from local videos through NVIDIA NVDEC, and audits image readability and provenance before final persistence.

The revised workflow includes **all 22,220 verified finding segments**, including **13,378 singleton segments**, with **`minimum_verified_segment_frames=1`**. The local planning check retained one verified target per segment and produced **110,666 in-bounds temporal references**, of which **43,760 references** were excluded from active evidence to preserve physical-frame split isolation. The remaining permitted references require **16,964 unique video-frame extraction requests**. These are input and planning results, not a claim that the ongoing Colab run has completed extraction or publication.

Pure table transformations remain separate from file copying, local hashing, GPU decoding, image auditing, and publication. The configured execution uses **32 shared copy workers**, a separate **1,000-worker CPU SHA-256 phase**, **10 concurrent NVDEC video workers**, and a **100 GB decimal SSD budget**. Final persistence reconciles only missing or different outputs. An unlabelled context frame has no ground-truth annotation; it must not be interpreted as normal, a verified clinical boundary, or continuous visibility of the target finding.

| Validated input loading | Reads the catalog-selected S1–S5 metadata from the pinned commit. Checks catalog identities, schemas, table fingerprints, producer certificates, raw-image/video references, and consumed-input hashes across sectors. Compressed Git exports and original producer bytes retain their respective checksum checks. S5 targets and their annotation collections are checked against the accepted member rows. Configuration is selected by the catalog, never by filename timestamp. |
| Shared local staging | Plans the required official images, eligible segments' videos, and producer metadata. Copies them from Drive through one rolling queue with 32 workers, allowing image, video, and metadata tasks to use the same pool. Runtime access paths are rebuilt from committed relative paths under the SSD root. No S6 result is written back to Drive at this stage. |
| Local SHA-256 and selective repair | Hashes existing local candidates and then newly copied files using a separate CPU pool configured for 1,000 concurrent tasks and streaming reads. Checks exact required-file coverage, byte sizes, SHA-256 values, and file-state consistency. Missing or different files alone are recopied and reverified. Drive is read for copying, never for a separate source-media hashing pass. Exhausted retries leave a local failure report and stop processing. |
| Temporal references and annotation metadata | Includes segments with at least one verified frame, independently of S5's multi-frame supervision flag. Uses S5's representative frame without selecting a new target. | NVDEC extraction and local image audit | Decodes SSD videos sequentially in display order with up to 10 independent NVDEC decoders and bounded GPU batches. Only requested frames cross to host memory for JPEG/PNG encoding. Images receive provenance sidecars, and compatible local outputs can be reused after verification. Image auditing uses nvImageCodec when supported and OpenCV CPU fallback; video decoding has no CPU fallback. Verified extraction evidence is reused, while official images are checked against inherited source hashes. |
| Calculation identity and final persistence | Binds the effective configuration, verified inputs, active code, and dependencies to the processing identity. Serializes and checks the in-memory result tables locally, including typed readback and file hashes. Only complete, validated results are reconciled to Drive; missing or different files are replaced and the catalog is installed last. Failed or planning-only bundles remain local diagnostics. |

## Outputs and scope

The final Drive metadata destination is `outputs/phase2/sector6/` relative to the configured mounted storage root; the GitHub destination has the same project-relative path. Runtime processing and local serialization use the SSD workspace. Saved table copies rebase their live image/video paths to persistent storage while retaining portable relative references.

The table below describes the revised producer's output contract. Its stable report/config filenames will become active after a successful new publication. Until then, the existing catalog continues to select the older timestamped files; consumers must follow its explicit entries rather than assume the new filenames already exist.

| Artifact | Purpose |
| --- | --- |
| `results/temporal_manifest.parquet` | Segment/offset evidence references, inherited targets and splits, annotation status, selected official or extracted image references, readability results, and diagnostic split exclusions. |
| `results/temporal_extraction_requests.parquet` | One deterministic request per unique permitted video/frame identity requiring extraction, with source and output references. |
| `results/extracted_temporal_frames.parquet` | Per-request extraction outcomes, errors, source-video and output-image SHA-256 values, and decoder provenance. |
| `reports/temporal_window_report.csv` | Requested, in-bounds, split-allowed, excluded, and usable context counts, with completeness flags per segment. |
| `reports/temporal_extraction_failures.csv`, `reports/temporal_image_audit.csv`, and `reports/temporal_status_report.csv` | Missing/unreadable evidence references, unique image readability/hash/dimension records, and aggregate evidence statuses. |
| Matching `*_schema.json` files beside the seven tables | Column types, null-restoration information, row counts, and fingerprints used for checked readback. |
| `configs/sector6_config.json`, `configs/sector6_lineage.json`, and [`configs/sector6_state.json`](configs/sector6_state.json) | Effective settings, consumed upstream identities and source provenance, processing identity, active artifact selection, and file-byte SHA-256 records. The transformation core receives explicit tables and configuration and returns new tables without filesystem or network access. GPU video decoding uses PyNvVideoCodec's high-level `SimpleDecoder` API; selected device frames are exchanged through DLPack and copied to host memory for JPEG/PNG encoding. Image decoding during the physical audit may use GPU support or OpenCV CPU fallback independently of NVDEC video decoding. The 1,000 hashing workers are a concurrency limit, not 1,000 physical CPU cores or a guaranteed speedup.

A **sidecar** is a separate metadata file stored next to an image. For example, `frame_00000120.jpg.provenance.json` accompanies `frame_00000120.jpg` and records the source-video hash, decoded-frame index, verified index offset, decoder/runtime identity, encoding settings, and image hash. A readable cached image is reused only when its identity and verified bytes match the current request.

- [PyNvVideoCodec Decoder API](https://docs.nvidia.com/video-technologies/pynvvideocodec/pynvc-api-reference/decoder.html)
- [NVIDIA API programming guide and interoperability](https://docs.nvidia.com/video-technologies/pynvvideocodec/pynvc-api-prog-guide/using_pynvvideocodec_apis.html)
- [NVIDIA parallel decoding samples](https://docs.nvidia.com/video-technologies/pynvvideocodec/read-me/running-samples.html#decode-perf-py)

Singleton eligibility supplies one verified anchor; it does not turn neighbouring frames into annotations or upgrade `single_frame_anchor_only` to multi-frame supervision. S6 preserves `verified_temporal_boundary_available=False`. Nominal FPS-based offsets and observed segment limits are not verified clinical onset/offset or exact variable-frame-rate timestamps. Official-image metadata retains source annotation identities and distinguishes frame-wide labels from labels attached to the selected image.

Input integrity is anchored in `main`. If S2 changes while S3–S5 still record the previous consumed hashes, loading fails instead of selecting an older configuration. If unrelated files change on `main`, unchanged consumed upstream blobs remain valid; a change to one of those consumed blobs requires a fresh load. Dataset hashes are read from the committed artifacts and are not hardcoded in the notebook.

On a rerun within the same Colab runtime, local inputs are reverified and only missing or different files are recopied. Compatible local extracted images can be reused. Unreferenced local cache files are not consumed but still count toward capacity. The initial output reserve and concurrent-write accounting protect the local budget; insufficient capacity stops processing rather than causing a fallback to Drive reads. After a runtime reset removes the local SSD contents, input staging and any unavailable local derived evidence must be rebuilt.

Final persistence compares the newly generated local outputs with destination content, skips identical files, replaces missing or different files, and commits the catalog last. An interrupted copy can be resumed without recopying matching destinations. Failed or planning-only runs retain local diagnostics and do not finalize Drive/GitHub outputs. Local-only `reports/input_staging_failures.json` is written when staging retries are exhausted; `configs/sector6_execution_receipt.json` records acquisition and reconciliation details outside the published artifact catalog.

Publication is controlled by `push` and `dry_run`. With both false, Git publication is not requested. A dry run prepares and checks Git changes without committing or pushing; it does not disable the earlier final Drive save. A successful ordinary push includes only selected S6 metadata and preserves this README and unrelated repository files. Matching remote blob identities require no output download or replacement. The stable lineage retains the commit that certified the bundle; an unrelated `main` advance is recorded in the local execution receipt without forcing a new metadata commit solely for operational counters.

The principal evaluation limit remains inherited from S4: the same labelled videos participate across supervised splits. Excluding conflicting physical-frame references prevents those references from being reused as model evidence across splits, but does not establish independent-video or independent-patient generalization or remove visual similarity between nearby frames. S6 does not track individual lesions, validate unlabelled findings, establish continuous clinical boundaries, repair upstream annotations, generate crops or collages, train models, or perform medical question answering.
